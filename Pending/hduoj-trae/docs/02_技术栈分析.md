## 四、架构设计模式分析

### 4.1 模块化分层
- **数据模型与业务逻辑分离**：`utils.py` 只负责数据结构和 I/O，不涉及 AI 或 UI
- **配置集中管理**：所有可调参数集中在 `config.py`，便于修改
- **插件式 LLM 接入**：通过 `provider` 参数切换，新增提供商只需在 `ProblemAnalyzer._init_llm()` 添加分支

### 4.2 状态管理
- **Session State 缓存**：`st.session_state` 存储 `analyzer`, `llm_provider`, `analyzed_problems`, `knowledge_graph` 四个全局状态
- **持久化缓存**：`analyzed_problems.json` 作为本地缓存，避免重复调用 LLM
- **惰性初始化**：图谱和分析器在首次使用时才构建

### 4.3 数据流设计
```
用户操作 → Streamlit 事件 → app.py 页面函数
    ├── 分析页面 → ProblemAnalyzer.analyze_batch() → LLM → 结果写入 JSON
    ├── 筛选页面 → get_all_tags() / filter_problems_by_tags() → 列表渲染
    └── 图谱页面 → KnowledgeGraph.build_graph() → visualize() → HTML 嵌入
```

## 五、技术栈亮点总结

| 维度 | 说明 |
|------|------|
| **前端快速原型** | 纯 Streamlit 实现，无需额外前端框架，开发效率高 |
| **多 LLM 兼容** | 同时支持本地（Ollama）和云端（OpenAI/DeepSeek/阿里云），灵活切换 |
| **可视化交互** | PyVis + vis.js 提供可拖拽、可缩放、可点击的交互式知识图谱 |
| **本地缓存策略** | 分析结果持久化为 JSON，支持断点续分析 + 跨会话复用 |
| **干净的分层** | 配置 / 模型 / 分析 / 图谱 / UI 各层职责单一，耦合度低 |

## 六、潜在优化方向

1. **数据库替代 JSON**：可引入 SQLite 或 DuckDB 替代 JSON 文件存储，支持更快的查询和索引
2. **异步 LLM 调用**：批量分析时使用 `asyncio` 并发调用，大幅提升吞吐
3. **向量数据库**：引入 Chroma/FAISS 实现语义搜索，替代关键词筛选
4. **前端框架升级**：Streamlit 适合原型，可考虑引入 React/Vue 做更复杂的交互
5. **API 化**：将分析引擎封装为 FastAPI 服务，分离前后端
6. **CI/CD**：加入 pytest 测试、代码格式化（black/ruff）、pre-commit hooks
